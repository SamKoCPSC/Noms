#### Error 1 & 2: `HtmlCanvasElement` not found (lines 299, 335) and `HtmlInputElement` not found (lines 804, 827)

**Root Cause**: `web-sys` is declared as a **top-level dependency** in `Cargo.toml` (lines 34-40), meaning it's compiled for ALL targets including the native `--bin noms` server binary. However, `web-sys` types like `HtmlCanvasElement` and `HtmlInputElement` are generated by `wasm-bindgen` from Web IDL and are **only available when the crate is compiled for the `wasm32` target**. Even though the code using these types is gated with `#[cfg(target_arch = "wasm32")]`, the `web-sys` crate itself must be target-scoped for its feature-gated types to resolve correctly.

**Evidence from codebase**:
- `Cargo.toml` line 34-40: `web-sys` with features including `HtmlCanvasElement`, `HtmlInputElement`, `File`, `FileReader`, etc. — all in top-level `[dependencies]`
- `Cargo.toml` lines 50-51: wasm32-specific section only has `dioxus-web = "0.7"`
- `src/utils/image_processing_client.rs` line 5: `#![cfg(target_arch = "wasm32")]` — this entire module is wasm32-gated, but it imports `web_sys::{Blob, CanvasRenderingContext2d, HtmlCanvasElement, HtmlImageElement}` at line 10
- `src/pages/settings/settings_profile.rs` line 277: `#[cfg(target_arch = "wasm32")]` on `process_avatar_image` function, which uses `use web_sys::HtmlCanvasElement;` at line 279
- `src/pages/settings/settings_profile.rs` lines 804, 827: `input.dyn_ref::<web_sys::HtmlInputElement>()` — used in onclick closures within the main component (NOT wasm32-gated at the function level, but the RSX only runs in web context)

**Fix for Cargo.toml** — Move `web-sys`, `js-sys`, `gloo-net`, and `gloo-timers` from top-level `[dependencies]` to `[target.'cfg(target_arch = "wasm32")'.dependencies]`:

3. It's also a transitive dependency of `dioxus` (via `dioxus-web`), so it's always available

#### Error 4: `auth_context` not mutable at line 700

**Root Cause**: At line 434, `auth_context` is declared as **immutable**: `let auth_context = use_context::<Signal<AuthContext>>();`. Inside the spawned async block at line 663, it's shadowed with `let mut auth_context = auth_context;`, but the compiler still requires the original binding to be mutable because the closure captures it and the shadowed `let mut` doesn't change the capture mode.

**Evidence from codebase**:
- Line 434: `let auth_context = use_context::<Signal<AuthContext>>();` — no `mut`
- Line 663: `let mut auth_context = auth_context;` — shadowing with `mut` inside wasm32 block

- Line 724: Same pattern in `on_remove_avatar` handler
- Line 737: `auth_context.write().current_user = Some(profile);` — requires mutable access

**Fix for `settings_profile.rs`** — Change line 434 from immutable to mutable:

```diff
-    let auth_context = use_context::<Signal<AuthContext>>();
```

This single change resolves the issue for ALL usages of `auth_context` throughout the component:
- Line 445: `auth_context.read().current_user` — works with both `&` and `&mut` (`.read()` takes `&self`)
- Line 469: `auth_context.read().current_user.clone()` — same

#### Error 5: `HtmlInputElement` used outside wasm32-gated context (lines 804, 827)

**Root Cause**: The `web_sys::HtmlInputElement` type is used in onclick closures within the main `SettingsProfile` component (lines 804, 827), which is NOT gated with `#[cfg(target_arch = "wasm32")]`. These closures use `doc.query_selector("#avatar-upload-input")` and `input.dyn_ref::<web_sys::HtmlInputElement>()` to programmatically click a hidden file input.

**Resolution**: This is resolved by the Cargo.toml fix above. Once `web-sys` is moved to the wasm32 target block, the `--lib --bin noms` check (native target) won't try to compile `web-sys` at all. The `SettingsProfile` component renders on both server (SSR) and client (wasm32). During SSR, the onclick closures are never executed (no browser DOM), and during client rendering (wasm32), `web-sys` is available.

However, there's a subtlety: the `SettingsProfile` component itself is compiled for both targets. The onclick closures reference `web_sys::window()`, `web_sys::HtmlInputElement`, etc. On the native target, these references won't compile because `web-sys` won't be in the dependency tree.

**Additional fix needed**: The onclick closures using `web_sys` need to be wrapped in `#[cfg(target_arch = "wasm32")]` or the code needs to use a different approach for SSR compatibility. Looking at the code:

```rust
onclick: move |_| {
    if let Some(window) = web_sys::window() {
        if let Some(doc) = window.document() {
            if let Some(input) = doc.query_selector("#avatar-upload-input").ok().flatten() {
                if let Some(file_input) = input.dyn_ref::<web_sys::HtmlInputElement>() {
                    file_input.click();
                }
            }
        }
    }
},
```

This code path only executes on the client (wasm32), but it's compiled for both targets. The fix is to wrap these closures with `#[cfg(target_arch = "wasm32")]` conditional compilation. In Dioxus/RSX, this can be done using `#[document::raw]` or by creating separate handler functions.

**Recommended approach**: Create helper functions gated by `#[cfg(target_arch = "wasm32")]`:

```rust
#[cfg(target_arch = "wasm32")]
fn trigger_file_input(id: &str) {
    if let Some(window) = web_sys::window() {
        if let Some(doc) = window.document() {
            if let Ok(Some(input)) = doc.query_selector(id) {
                if let Some(file_input) = input.dyn_ref::<web_sys::HtmlInputElement>() {
                    file_input.click();
                }
            }
        }
    }
}

#[cfg(not(target_arch = "wasm32"))]
fn trigger_file_input(_id: &str) {
    // No-op during SSR
}
```

Then use in RSX: `onclick: move |_| trigger_file_input("#avatar-upload-input")`

```rust
pub async fn update_avatar_url(
    executor: impl sqlx::Executor<'_, Database = Postgres>,
    user_id: Uuid,
    avatar_url: Option<&str>,
) -> Result<User, DbError> {

        User,

    )
    .fetch_one(executor)
    .await
    .map_err(DbError::Query)
}
```

#### Step 2: Create `src/api/avatar.rs`

**New file**: `src/api/avatar.rs`

This module contains two server functions:

```rust
//! Avatar upload and removal server functions.
//!
//! Reuses the existing upload pipeline (WebP validation, StorageClient)
//! but stores under the `avatars/` prefix instead of `recipes/`.
#![cfg_attr(not(feature = "server"), allow(dead_code, unused_imports))]

use dioxus::prelude::*;
use crate::api::upload::{UploadResponse, validate_webp_magic, MAX_FILE_SIZE};
use crate::auth::context::UserProfile;
use crate::storage::get_storage_client;

const AVATAR_MAX_SIZE: usize = 5 * 1024 * 1024; // 5 MB for avatars (smaller than recipe images)

/// Upload a profile avatar image.
///
/// Validates WebP magic bytes, stores the image under `avatars/{user_id}/{uuid}.webp`,
/// updates the user's avatar_url in the database, and returns the UploadResponse.
///
/// If the user already has an avatar, the old image is deleted from storage (best-effort).
#[server]
pub async fn upload_avatar(
    full_bytes: Vec<u8>,
    thumb_bytes: Vec<u8>,
) -> Result<UploadResponse, ServerFnError> {
    let user_id = crate::auth::session::extract_user_id_from_fullstack()
        .await
        .ok_or_else(|| ServerFnError::new("Not authenticated"))?;

    // Validate file sizes (avatars have a smaller limit)
    if full_bytes.len() > AVATAR_MAX_SIZE {
        return Err(ServerFnError::new(
            "Avatar image too large. Maximum size is 5MB.",
        ));
    }
    if thumb_bytes.len() > AVATAR_MAX_SIZE {
        return Err(ServerFnError::new(
            "Avatar thumbnail too large. Maximum size is 5MB.",
        ));
    }

    // Validate WebP magic bytes (defense-in-depth)
    if !validate_webp_magic(&full_bytes) {
        return Err(ServerFnError::new(
            "Invalid avatar image. Expected WebP format.",
        ));
    }
    if !validate_webp_magic(&thumb_bytes) {
        return Err(ServerFnError::new(
            "Invalid avatar thumbnail. Expected WebP format.",
        ));
    }

    let storage = get_storage_client();
    let pool = crate::db::get_pool();

    // Fetch current avatar URL for cleanup
    let current_user = crate::db::get_user_by_id(&pool, user_id)
        .await
        .map_err(|e| ServerFnError::new(e.to_string()))?
        .ok_or_else(|| ServerFnError::new("User not found"))?;

    // Generate new storage keys: avatars/{user_id}/{uuid}.webp and -thumb.webp
    let unique_id = uuid::Uuid::new_v4();
    let full_key = format!("avatars/{}/{}.webp", user_id, unique_id);
    let thumb_key = format!("avatars/{}/{}-thumb.webp", user_id, unique_id);

    // Upload new avatar to storage
    let full_url = storage
        .put_object(&full_key, &full_bytes, "image/webp")
        .await
        .map_err(|e| {
            tracing::error!(error = %e, "Failed to upload avatar to storage");
            ServerFnError::new("Failed to upload avatar")
        })?;
    let _thumb_url = storage
        .put_object(&thumb_key, &thumb_bytes, "image/webp")
        .await
        .map_err(|e| {
            tracing::error!(error = %e, "Failed to upload avatar thumbnail to storage");
            ServerFnError::new("Failed to upload avatar")
        })?;

    // Update user's avatar_url in database
    crate::db::update_avatar_url(&pool, user_id, Some(&full_url))
        .await
        .map_err(|e| ServerFnError::new(e.to_string()))?;

    // Delete old avatar from storage (best-effort)
    if let Some(old_url) = current_user.avatar_url {
        let public_url = storage.public_url().trim_end_matches('/');
        if let Some(old_key) = old_url.strip_prefix(public_url).map(|s| s.trim_start_matches('/')) {
            let _ = storage.delete_object(old_key).await;
            // Also try to delete old thumbnail
            if let Some(old_base) = old_key.strip_suffix(".webp") {
                let _ = storage.delete_object(&format!("{}-thumb.webp", old_base)).await;
            }
        }
    }

    tracing::info!(full_key = %full_key, user_id = %user_id, "Uploaded avatar");
    Ok(UploadResponse {
        full_url,
        thumb_url: format!("{}/{}", storage.public_url().trim_end_matches('/'), thumb_key),
        key: full_key,
    })
}

/// Remove the authenticated user's profile avatar.
///
/// Deletes the avatar image from storage (best-effort) and clears
/// the avatar_url in the database.
#[server]
pub async fn remove_avatar() -> Result<(), ServerFnError> {
    let user_id = crate::auth::session::extract_user_id_from_fullstack()
        .await
        .ok_or_else(|| ServerFnError::new("Not authenticated"))?;

    let storage = get_storage_client();
    let pool = crate::db::get_pool();

    // Fetch current avatar URL
    let current_user = crate::db::get_user_by_id(&pool, user_id)
        .await
        .map_err(|e| ServerFnError::new(e.to_string()))?
        .ok_or_else(|| ServerFnError::new("User not found"))?;

    // Delete old avatar from storage (best-effort)
    if let Some(old_url) = current_user.avatar_url {
        let public_url = storage.public_url().trim_end_matches('/');
        if let Some(old_key) = old_url.strip_prefix(public_url).map(|s| s.trim_start_matches('/')) {
            let _ = storage.delete_object(old_key).await;
            // Also try to delete old thumbnail
            if let Some(old_base) = old_key.strip_suffix(".webp") {
                let _ = storage.delete_object(&format!("{}-thumb.webp", old_base)).await;
            }
        }
    }

    // Clear avatar_url in database
    crate::db::update_avatar_url(&pool, user_id, None)
        .await
        .map_err(|e| ServerFnError::new(e.to_string()))?;

    tracing::info!(user_id = %user_id, "Removed avatar");
    Ok(())
}
```

**Key design decisions**:
- Avatar size limit is 5MB (smaller than recipe images' 10MB) — avatars are small
- Storage keys use `avatars/{user_id}/{uuid}.webp` pattern (no `_full` suffix, just `.webp`)
- On upload, old avatar is deleted from storage (best-effort) before new one is set
- On remove, old avatar is deleted from storage (best-effort) before DB is cleared
- Reuses `validate_webp_magic` and `MAX_FILE_SIZE` pattern from `upload.rs`

**Note on `validate_webp_magic` visibility**: Currently `validate_webp_magic` is a private function in `upload.rs`. We need to either:
- **Option A (preferred)**: Make `validate_webp_magic` `pub` in `upload.rs` so `avatar.rs` can import it
- **Option B**: Duplicate the function in `avatar.rs`
- **Option C**: Move `validate_webp_magic` to a shared module (e.g., `src/api/common.rs`)

**Recommendation**: Option A — make it `pub fn validate_webp_magic` in `upload.rs`. This is the simplest change and avoids duplication.

### Architectural Decisions & Trade-offs

1. **Avatar storage keys**: `avatars/{user_id}/{uuid}.webp` (no `_full`/`_thumb` suffix pattern). Rationale: avatars are single-purpose; the `-thumb` suffix is sufficient to distinguish variants.

2. **Avatar size limit**: 5MB (vs 10MB for recipe images). Rationale: avatars are small profile photos; no need for the larger limit.

3. **Old avatar cleanup**: Best-effort deletion on upload and remove. Rationale: if old deletion fails, the orphan cleanup worker (CP11) will eventually clean it up. No need to block the user experience.

4. **Inline upload vs ImageUpload component**: Chose inline upload for simplicity. The `ImageUpload` component is over-engineered for a single avatar file (drag-drop, multi-file, compression toggle, progress tracking). A simple file input + canvas processing is sufficient.

5. **No new DB migration needed**: The `avatar_url` column already exists in the schema. No migration file needed.

6. **Auth context update on avatar change**: After upload or removal, we update `auth_context.write().current_user` so the avatar reflects immediately across the app (navbar, etc.) without a page reload.

### Potential Gaps / Areas Needing Follow-up

1. **`StorageClient::public_url()` return type**: Need to verify the exact return type and whether it includes a trailing slash. The avatar code assumes `public_url().trim_end_matches('/')` works.

2. **`ImageUpload` component's `upload_fn` callback**: If we decide to reuse `ImageUpload` instead of inline upload, we need to understand its callback signature and whether it can be wired to `upload_avatar` instead of `upload_image`.

3. **Avatar aspect ratio**: The spec doesn't mention cropping for avatars. The inline upload can resize but not crop. A square crop would be ideal for circular avatars (CP9 crop editor could handle this later).

4. **OAuth avatar vs uploaded avatar priority**: The current UI shows "Provided by your OAuth provider". After this change, the priority should be: uploaded avatar → initials fallback. The OAuth avatar URL (if any) is not currently stored in the DB; it comes from the OAuth flow. We should clarify whether OAuth avatars are stored anywhere or just used as a temporary fallback.

#### 3. `src/pages/settings/settings_profile.rs` — Major avatar section rewrite

This is the largest change. The file now contains:

**Client-side image processor** (`wasm32` only):
- `process_avatar_image(web_file: web_sys::File) -> Result<ProcessedAvatar, String>` — loads the file via the existing `load_image_from_file` utility, draws it center-cropped onto a canvas, and exports two WebP variants: 400x400 full (quality 0.9) and 100x100 thumbnail (quality 0.8). Returns `ProcessedAvatar { full_bytes: Vec<u8>, thumb_bytes: Vec<u8> }`.
- Reuses `blob_from_canvas` from `image_processing_client.rs` rather than duplicating canvas logic.

**Server function `upload_avatar`** (inline `#[server]`):
1. Extracts the authenticated user ID via `extract_user_id_from_fullstack()`.
2. Validates file sizes (2MB limit for both full and thumb variants).
3. Validates WebP magic bytes on both variants via `validate_webp_magic`.
4. Fetches the current user to get their existing `avatar_url` for cleanup.
5. Generates storage keys: `avatars/{user_id}/{uuid}.webp` and `avatars/{user_id}/{uuid}-thumb.webp`.
6. Uploads both variants to storage via `StorageClient::put_object`.
7. Updates the DB via `update_avatar_url`.
8. **Best-effort cleanup**: deletes the old avatar and its thumbnail from storage by deriving the storage key from the old URL.
9. Returns the updated `UserProfile`.

**Server function `remove_avatar`** (inline `#[server]`):
1. Extracts the authenticated user ID.
2. Fetches the current user to get their existing `avatar_url`.
3. **Best-effort cleanup**: deletes the old avatar and thumbnail from storage.
4. Clears `avatar_url` in the DB via `update_avatar_url` with `None`.
5. Returns the updated `UserProfile`.

Both server functions are annotated with `#[cfg_attr(not(feature = "server"), allow(dead_code, unused_imports))]` to suppress warnings on the wasm32 target.

### Dependencies

- **No new external dependencies** were introduced. The implementation exclusively reuses existing crates and utilities.
- **Internal dependencies**: `src/api/avatar` server functions depend on `src/db/mod.rs` (`update_avatar_url`, `get_user_by_id`, `get_pool`), `src/storage.rs` (`get_storage_client`, `StorageClient`), and `src/api/upload.rs` (`validate_webp_magic`). The UI in `settings_profile.rs` depends on `src/auth/context.rs` (`UserProfile`, `AuthContext`), `src/utils/image_processing_client.rs` (`load_image_from_file`, `blob_from_canvas`), and `src/auth/session.rs` (`extract_user_id_from_fullstack`).

### Special Patterns and Language Features

- **Dioxus `#[server]` macro**: Both `upload_avatar` and `remove_avatar` are defined as inline server functions within a UI module. The macro handles conditional compilation — the function body only compiles on the server target, while a stub is generated for wasm32.
- **`#[cfg_attr(not(feature = "server"), allow(dead_code, unused_imports))]`**: Suppresses dead_code warnings for server-only items when compiling for the wasm32 target.
- **Center-crop on canvas**: The `process_avatar_image` function uses `drawImage` with calculated source rectangles to center-crop non-square images before resizing, ensuring the avatar preview is always square.
- **Best-effort storage cleanup**: Old avatar deletion uses `let _ = storage.delete_object(...).await;` to ignore errors. Orphaned files are handled by the CP11 orphan cleanup worker.

### Follow-up Recommendations

1. **Dedicated `src/api/avatar.rs` module**: The blueprint called for a separate module. The inline approach works but deviates from the `recipe.rs`/`upload.rs` pattern. Consider extracting to a dedicated module if avatar functionality grows.
2. **Integration tests for server functions**: No integration tests were written for `upload_avatar` or `remove_avatar`. Consider adding wiremock-based tests following the pattern in `upload.rs`.
3. **Avatar aspect ratio / crop editor**: The current center-crop is automatic. A CP9 crop editor would give users more control over how their avatar is framed.
4. **OAuth avatar priority**: Clarify whether OAuth-provided avatar URLs should be stored in the DB and used as a fallback when no uploaded avatar exists.
